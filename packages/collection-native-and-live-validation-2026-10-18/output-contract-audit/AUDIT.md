# Read-only audit of corpus delivery compatibility

Scope: current collector/exporter source inspected against the October 15 handoff and current implementation contract. Representative retained artifacts were read, not reparsed. No collection, browser, network, PDF/image API, source mutation, Git operation, or full-corpus normalization was performed. `source-bindings.json` pins the source bytes cited here; `observed-artifacts.json` pins the representative files and records their exact header/envelope/first-record observations. This audit does not grant any new source-completeness or legal-edition qualification.

## Finding

The current collector layer has documented, generally richer family-specific internal records and evidence ledgers. It does **not currently provide a uniform exporter to the original 16-field delivery interface**. Its normal collection/verification routes emit JSONL and family-specific convenience CSVs; Gridics and native Word emit no CSV at all. This is a compatibility/package-generation gap, distinct from source acquisition/content-fidelity gaps. Historical October 15 pipelines and the copied ICC legacy exporters demonstrate the requested interface, but their existence does not make it an output of the current common launcher.

Do not repair this by replacing the rich IR, reclassifying page records as legal sections, or treating CSV success as publication readiness. A pure, separately tested, source-bound packaging projection is the smallest maintainable integration.

## What the two contracts actually say

- Original `packages/local-extraction-handoff-2026-10-15/OUTPUT-CONTRACT.md:3` calls itself the **proposed delivery contract**, distinguishes the **existing 16-column corpus convention**, and introduces source-node/provenance sidecars without changing that interface. The accompanying handoff README calls it “Required artifacts” at line18 and says produce those artifacts at line53. It is therefore a concrete handoff format to implement, not evidence that all current collectors already implement it.
- Original lines7–28 require a jurisdiction directory, publication subdirectories, manifest/publication/source-node/disposition/provenance/validation/exception artifacts, per-publication fulltext/TOC JSON+CSV, and aggregate equivalents. Lines30–32 explain the publication-scope and manifest contents.
- Lines36–44 prescribe exactly these ordered fields: `jurisdiction, code_name, division, title, subtitle, chapter, subchapter, article, part, subpart, section_number, section_name, citation, full_text, source_url, scrape_date`; JSON `{metadata, provisions}`; UTF-8 BOM CSV; row-for-row equality; derived TOC with identical order/identities and blank `full_text`. The source inventory is independent of that derived TOC.
- Lines50–68 are **recommended source-node field names/example**, not a mandatory literal JSON schema. Line70 requires stable publisher IDs or documented source-backed local locators. Lines72–83 require one disposition per source node and record-level provenance. Different internal names can satisfy the same information requirement; missing named sidecar files alone does not show missing provenance.
- Lines81,87–89 require own parent bodies, structured HTML/XML, table/list/note fidelity and PDF page/coordinate evidence plus logical continuation/reading order. Lines93–104 distinguish downstream readiness from HTTP success or row counts. The current user image rule supersedes the earlier readable-image/transcription clause: exact `[IMAGE]`, no separate image acquisition/decoding/extraction/render/OCR (`collectors/README.md:47–49,100–108`; `IMAGE-POLICY.md`).
- Current `collectors/IMPLEMENTATION-CONTRACT.md:8–14` requires full dynamic traversal, source identity, rich retained records, checkpoints, separate coverage dimensions, a read-only source verifier and a documented output schema. It does **not** itself specify the 16 fields, JSON envelope, BOM, or artifact filenames. Its line15 explicitly permits representative genuine publication-level validation and forbids relabeling partial scopes; no requirement to run all jurisdictions can be inferred. Current root README100 explicitly reconnects full-publication acceptance to original content-fidelity requirements.

Every current CSV implementation above writes a convenience projection; it is not the 16-column contract. The inspected actual CSVs all began with ordinary field-name bytes, not `EF BB BF`. Current CSV verifies generally match those internal projections, which is useful but not validation of the legacy JSON/CSV/TOC triad. Official `verify.py:18–20` checks row IDs/text (not every convenience column); stronger byte-equivalent export verification can be added in the new pure packaging layer without touching acquisition.

## Historical serializers and actual files that do meet the interface

- `collectors/ecode/legacy_ecode.py:25,236–249` has the exact 16 fields, `{metadata, provisions}` JSON, BOM CSV, round-trip validation, aggregate and per-publication fulltext/TOC outputs. Its metadata explicitly labels a validation sample. `legacy_municipal.py:240–261` also emits these pairs and source-node/disposition/provenance/exception/publication/validation/run-manifest sidecars, retaining incomplete source-validation status. These are real, reusable precedents, **not the current engine's normal output**.
- Inspected retained October 15 Malibu eCode360, Petaluma municipal.codes, and Flagstaff CodePublishing exports all had exactly16 columns, BOM, and metadata/provisions envelope. Their parent directories contained the named aggregate/publication/sidecar artifacts. Only representative rows were compared here; this audit is not a new whole-output row-equality or completeness certification.
- `full_text` representation is not identical even in these historical artifacts: the inspected Malibu/Petaluma rows are text; Flagstaff contains paragraph HTML. Original contract87 requires preserving structure but does not specify a new universal HTML-string schema. An integration should explicitly document one lossless representation and preserve richer source IR rather than silently normalize all full_text to flat strings.

## Minimal maintainable integration proposal — not implemented by this audit

1. Add an **offline packaging module**, with a small source-family projection interface and one shared writer/verifier. Leave acquisition, rate gates, source parsers, historical outputs and current internal verifiers unchanged. Command shape could be `package --input VERIFIED_RUN --publication EXACT_ID --out FRESH_DIR`, with explicit manifest selection for multi-publication jurisdiction assembly. This is a proposal, not an existing command.
2. Each family reader returns source-backed publication metadata, ordered inventory/dispositions, and typed canonical own-body records with stable source IDs and raw locators. It must select canonical structures from current records, excluding `superseded_detector_diagnostics` from text/table export while preserving them in evidence. Unknown hierarchy, currency, or section grouping stays explicit; do not infer it to fill a CSV column.
3. Build exactly16 string fields using explicit source hierarchy and literal displayed heading/citation. Keep unnumbered/repeated source bodies. Fill inapplicable hierarchy/number fields with empty strings and carry typed original hierarchy/identity decisions in provenance. Preserve acquisition time as scrape_date with documented precision; do not use replay time or call a publisher “updated” label a legal effective date. Preserve source version separately from source node identity. Avoid Bluebook conversion or any legal/drafting correction.
4. Use canonical sanitized semantic HTML when available for lossless paragraph/list/table/span/note/sup/sub order; retain structured IR and original raw bytes. For qualified native structures, serialize only verified logical/physical structures with explicit unit/scope metadata. Do not fabricate legal section grouping from physical pages. Exact `[IMAGE]` stays at owned source positions; export performs no image fetch/decode/render/OCR and does not reintroduce embedded image payloads. Unqualified native reading order/Unicode/table/edition remains incomplete, even if a draft compatibility file can be written.
5. Emit the exact JSON/CSV/fulltext/TOC/publication/aggregate artifact set in a fresh directory. CSV uses explicit `encoding='utf-8-sig', newline=''`, standard quoting, stable source order and literal values; JSON uses `{metadata, provisions}`. Include original richer records as an immutable referenced IR artifact rather than attempting to cram their full evidence into the16 columns. Sidecars map each corpus row to stable publication/node IDs, source version and raw hashes; all paths relative to the delivered root. Raw snapshots can be copied or included by a hash-verified package boundary, not unresolved absolute development paths.
6. Read-only package verification should validate: exact ordered fields/BOM; full CSV↔JSON equality including embedded newlines/quotes and Unicode; TOC identity/order with blank full_text; aggregate/per-publication equality; one source-node disposition each; included output-ID/row mapping; raw/source/version/parser hash bindings; canonical own-body ownership; all discovered-family scope dispositions; and unchanged independent source-completeness dimensions. Test duplicate printed locators, unnumbered parent bodies, table spans/notes/lists, corrected canonical versus diagnostic grids, cross-page continuations, [IMAGE] placement, missing/corrupt raw, wrong version and interrupted packaging. Package status can be `incomplete` with explicit exceptions; only an all-required-dimensions verified package can be called downstream-ready.

This can start with one verified HTML publication and a meaningful source-sensitive fixture per family, without acquiring any more source or rerunning full corpora. Native-only page and Word-unit modes should initially be exported explicitly as incomplete until their logical section/reading-order requirements are genuinely established. No scope/schema waiver or blanket semantic acceptance is needed.

## Inspection limits

No new whole-corpus fidelity judgment is made. Actual-output observations are format/schema/header/representative-record checks, not a revalidation of all cells, sections or source versions. Source code citations describe the hash-pinned current source; retained artifacts may have an older captured execution revision and are labelled by exact path. Existing publisher stops, unresolved references, native font/edition issues and live interruption jobs are untouched. The original handoff's recommended source-node example is not elevated into a mandatory expanded schema, and packaging sidecar projection is not mistaken for already-delivered output.
